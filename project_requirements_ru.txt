Курсовой проект

Используйте следующее (в зависимости от того, в какой вы группе):
.NET: C# (обязательно), Blazor или MVC (на ваш выбор); разумеется, используйте JavaScript или TypeScript по мере необходимости; SQL Server/MySQL/PostgreSQL
или
PHP: PHP, Symfony; разумеется, используйте JavaScript или TypeScript по мере необходимости; MySQL/PostgreSQL

Используйте CSS-фреймворк (рекомендуется Bootstrap, но можно любой).

Вы можете использовать любые другие библиотеки, компоненты и даже фреймворки (но не заменять ими указанные выше).

Ограничений по архитектуре и используемым сервисам нет. Например, от вас не требуется иметь отдельный полноценный сервер приложений, отделённый от веб-сервера, или выносить много логики на клиент, или использовать микросервисы и т. п.; подходите к этому так, как считаете нужным.

Для хранения данных рекомендуется использовать самый простой и надёжный подход, а именно реляционную базу данных, например PostgreSQL, MySQL, SQL Server. Ещё раз: вы можете заменить Bootstrap на любой CSS-фреймворк и/или UI-библиотеку, которая вам нравится.

Идея
Вам нужно реализовать веб-приложение — систему управления резюме (различные позиции, опыт, навыки и т. д.). Пользователи определяют «позиции» с набором атрибутов. Позиция — это своего рода шаблон для резюме; другие пользователи заполняют свои резюме для соответствующих позиций конкретными значениями. Три важнейшие возможности — это настраиваемые позиции с произвольными атрибутами, переиспользуемая библиотека атрибутов и автоматическая генерация резюме.

Например, рекрутер создаёт позицию «Бизнес-аналитик», добавляет атрибут-выпадающий список «Уровень английского» и числовое поле «Средний балл». Некоторые кандидаты заполняют уровень английского и средний балл в своих профилях и генерируют резюме, адаптированные под данную позицию. Затем рекрутеры просматривают резюме, чтобы найти подходящего кандидата.

# Предупреждение
Если в вашем приложении будет N кнопок (просмотр/редактирование/удаление в _каждой_ записи), ваш результат будет снижен на 20%. Используйте панели инструментов или анимированно «появляющиеся» контекстные действия и т. п.

Так делать запрещено:
```

├─────────────┼─────────────────┼ ┼────────────────┤

├─────────────┼─────────────────┼ ┼────────────────┤
                        …
├─────────────┼─────────────────┼ ┼────────────────┤
│ Morris, Lee │ QA Engineer     │…│ [Edit][Delete] │
└─────────────┴─────────────────┴ ┴────────────────┘
```
А так — нормально:
```
[Delete]

 ⍰  𝗡𝗮𝗺𝗲 v        𝗣𝗼𝘀𝗶𝘁𝗶𝗼𝗻               𝗟𝗲𝘃𝗲𝗹
```

Позиции, как и резюме, должны отображаться в табличном представлении.

Использование представления в виде «плиток» / «галереи» снизит оценку на 20%.

Так делать неправильно:

На каждой странице должен быть доступ к полнотекстовому поиску через верхнюю шапку.

> Реализуйте в своём приложении удобную и последовательную навигацию.

# Обзор
Система представляет собой веб-платформу для подбора персонала, которая позволяет кандидатам вести переиспользуемые профессиональные профили и генерировать резюме, адаптированные под позиции, которыми управляют рекрутеры.

Платформа построена вокруг трёх «киллер-фич»:
* Переиспользуемая библиотека атрибутов — атрибуты можно определить один раз и переиспользовать в нескольких позициях и резюме;
* Настраиваемые шаблоны позиций — рекрутеры могут собирать шаблоны резюме под конкретную позицию, используя атрибуты из библиотеки;
* Автоматически генерируемые резюме — резюме собираются динамически из данных профиля кандидата и требований позиции.

Платформа поддерживает три роли пользователей:
* Кандидат;
* Рекрутер;
* Администратор.

# Аутентификация
Неаутентифицированные пользователи могут:
* Зарегистрировать учётную запись;
* Войти в систему;
* Просматривать доступные позиции в режиме только для чтения;
* Просматривать публичную статистику (например, «10 новых резюме создано за последние 24 часа»).

Неаутентифицированные пользователи не могут: создавать или редактировать позиции, просматривать или создавать резюме, оставлять комментарии или ставить лайки резюме, заходить на персональные страницы.

Пользователи могут аутентифицироваться через провайдеров социального входа (как минимум платформа должна поддерживать двух). Хорошие варианты — Google и Facebook, но вы можете выбрать других.


# Роли
Кандидаты могут:
* Управлять своим персональным профилем;
* Выбирать и заполнять атрибуты из библиотеки атрибутов;
* Управлять описаниями проектов;
* Просматривать доступные им позиции;
* Создавать и редактировать резюме для позиций, к которым им разрешён доступ (если кандидат теряет доступ, заполненные резюме скрываются);
* Участвовать в обсуждениях.

Кандидаты могут иметь доступ только к своему собственному профилю и своим резюме.

Все рекрутеры несут совместную ответственность за один и тот же набор позиций. Любой рекрутер может изменить любую позицию, понятия владения позицией не существует. Кроме того, все рекрутеры управляют общим пулом атрибутов.

Любой рекрутер может:
* Создавать позиции;
* Дублировать существующие позиции;
* Редактировать позиции;
* Удалять позиции;
* Настраивать правила доступа;
* Управлять шаблонами позиций;
* Управлять библиотекой атрибутов;
* Просматривать резюме кандидатов в режиме только для чтения (с помощью полнотекстового поиска, через позицию или через персональные страницы);
* Участвовать в обсуждениях;
* Ставить лайки резюме.

Администраторы имеют неограниченный доступ. Админы обладают полным доступом и могут просматривать все страницы так, как если бы они были их владельцами. Например, админ может открыть страницу кандидата, исправить опечатки, отредактировать атрибуты или внести любые другие изменения — фактически выступая владельцем любой персональной страницы.

Администраторы могут:
* Просматривать все страницы;
* Редактировать любой профиль кандидата;
* Редактировать любое резюме;
* Редактировать любую позицию;
* Выполнять все действия рекрутера;
* Выполнять все действия кандидата;
* Управлять пользователями (просмотр, блокировка, разблокировка, удаление, назначение ролей, снятие ролей).

> Администраторы могут снять роль администратора с самих себя.


# Персональный профиль
У каждого аутентифицированного пользователя есть страница персонального профиля. Редактировать или просматривать профиль целиком могут только владелец профиля и администраторы.

Рекрутеры не имеют доступа к редактированию профиля и видят данные резюме только как страницу в режиме чтения.

Профиль состоит из четырёх разделов:
## Обо мне (Me)
Содержит обязательные встроенные атрибуты. Эти атрибуты существуют всегда и не могут быть удалены. Например: имя, фамилия, местоположение, личное фото. Эти атрибуты должны быть построены на том же «движке» (например, их можно добавить в шаблон позиции), но рекрутеры не могут их удалить.
## Информация (Info)
Содержит атрибуты, выбранные пользователем из библиотеки атрибутов.

Кандидаты могут:
* Добавлять атрибуты из библиотеки или удалять их;
* Заполнять значения этих атрибутов.

Например: баллы IELTS, навыки презентации, готовность к удалённой работе.
## Проекты (Projects)
Кандидаты могут вести список проектов.

Каждый проект содержит:
* Название;
* Период (диапазон дат);
* Описание (с Markdown-форматированием);
* Технологические теги (с поддержкой автодополнения по ранее введённым тегам; используйте хороший UI-компонент для тегов).

Проекты можно добавлять, редактировать и удалять.
## Резюме (CVs)
Отображает все резюме, созданные кандидатом. У кандидата может быть не более одного резюме на позицию. Существующие резюме можно редактировать или удалять. Новые резюме можно создавать только для позиций, доступных кандидату. Каждая запись резюме служит ссылкой на соответствующую страницу резюме.

# Автосохранение
Страницы персонального профиля поддерживают автоматическое сохранение:
* Изменения отслеживаются локально;
* Сохранение происходит каждые 5–10 секунд;
* Сохранение не должно происходить при каждом нажатии клавиши;
* Механизм автосохранения должен использовать оптимистичную блокировку.

Система обязана использовать оптимистичную блокировку. Каждая операция сохранения (для атрибутов, позиций и автосохранений профилей):
* Отправляет текущий номер версии;
* Обновляет запись, если версия совпадает;
* Возвращает новый номер версии;
* Завершается ошибкой, если версия изменилась.

Клиент должен корректно обрабатывать конфликты версий.


# Киллер-фича №1: Библиотека атрибутов
Библиотека атрибутов обеспечивает переиспользование структурированных данных в профилях, позициях и резюме.

Все рекрутеры могут: создавать атрибуты, редактировать атрибуты, удалять атрибуты.

Каждый атрибут содержит:
* Категорию — одну из предопределённого списка;
* Название — глобально уникальное имя атрибута;
* Некое описание;
* Тип данных атрибута.

Примеры категорий: сертификация, знание предметной области, персональная информация, soft skills.

Поддерживаемые типы атрибутов:
* Строка (однострочный простой текст);
* Текст (текст с Markdown-форматированием);
* Изображение (внешнее облачное хранилище, загрузка перетаскиванием);
* Число;
* Дата;
* Период (диапазон дат);
* Логический (флажок);
* Один из многих (выпадающий список).

Поскольку библиотека может стать большой, выбор атрибутов должен поддерживать:
* Поиск по префиксу;
* Недавно использованные атрибуты;
* Фильтрацию по категории.

# Киллер-фича №2: Позиции
Позиции служат настраиваемыми шаблонами резюме.

Все рекрутеры управляют общим списком позиций. Рекрутер может:
* Создать пустую позицию или продублировать существующую;
* Отредактировать любую позицию;
* Удалить любую позицию.

Каждая позиция содержит:
* Основную информацию, включая название и краткое описание;
* Правила доступа (позиция может быть либо публичной (доступной всем аутентифицированным пользователям), либо ограниченной с помощью фильтров);
* Атрибуты, выбранные из библиотеки атрибутов;
* Теги проектов (для выбора релевантных проектов), а также максимальное число проектов, включаемых в сгенерированное резюме.

Примеры правил доступа:
* Числовое значение «баллы IELTS» > 7.0;
* Флажок «удалённая работа» отмечен;
* Значение «навыки презентации» в выпадающем списке = «продвинутый».

Доступные операторы фильтрации зависят от типа атрибута.

Каждая позиция предоставляет список резюме, созданных по этой позиции (доступен только рекрутерам и администраторам).

Кандидаты могут создавать резюме только для тех позиций, к которым у них есть доступ. Если кандидат теряет доступ, уже созданные резюме не удаляются, а скрываются в интерфейсе.

Было бы неплохо иметь какие-нибудь дополнительные атрибуты позиции, например «Компания», «Уровень» (Junior/Middle/Senior/C-level) и т. п., чтобы фильтровать/сортировать позиции в таблицах, однако это не критично.


# Киллер-фича №3: Генерация резюме
Резюме генерируются автоматически из:
* Данных профиля кандидата (неудаляемые атрибуты, такие как имя);
* Выбранных атрибутов библиотеки (значения подтягиваются автоматически из атрибутов, заданных кандидатом);
* Проектов кандидата (отфильтрованных).

Когда пользователь редактирует атрибут в резюме, атрибут добавляется в профиль (если нужно; некоторые могут быть уже заполнены из профиля); атрибуты, отсутствующие в профиле, по умолчанию пусты.

Сгенерированное резюме должно:
* Быть профессионально оформленным;
* Быть разделено на чётко структурированные секции;
* Отображать только релевантную информацию (атрибуты, указанные в позиции, и отфильтрованные проекты).

Когда кандидат открывает своё резюме:
* Атрибуты автоматически предзаполняются из профиля;
* Недостающую информацию можно ввести вручную по месту.

> Каждый атрибут в резюме можно редактировать по месту (хранится единственное общее эталонное значение атрибута — в профиле). Если значение пустое, оно подсвечивается красным цветом.

Редактирование атрибута в резюме _изменяет исходное значение в профиле_.

Рекрутеры могут просматривать резюме только в отрендеренном режиме чтения; пустые значения подсвечиваются красным. Они не могут напрямую изменять резюме кандидатов (администраторы могут).

> Необходимо отслеживать состояния резюме, например с помощью отдельного действия «Опубликовать», доступного только тогда, когда заполнены все атрибуты. Это действие сделает резюме видимым для рекрутеров.


# Обсуждения
Каждая позиция содержит вкладку «Обсуждение». Сообщения в обсуждении включают: имя автора, отметку времени, текстовое содержимое (с Markdown-форматированием).

Если страницу просматривает рекрутер, имя автора является ссылкой на публичное представление профиля пользователя.

Сообщения отображаются в хронологическом порядке. Новые сообщения всегда добавляются в конец, вставлять сообщения между существующими нельзя. Обновления должны появляться у всех активных зрителей в течение 2–5 секунд (реализация может использовать WebSocket, опрос (polling) или что угодно ещё).

# Лайки
Каждое резюме поддерживает лайки.

Ставить лайки резюме могут только рекрутеры. Один рекрутер может поставить не более одного лайка конкретному резюме. Рекрутер может убрать свой лайк. Общее количество лайков отображается в списках резюме и в результатах поиска.

# Главная страница
Главная страница содержит:
* Последние позиции (таблица с недавно созданными или обновлёнными позициями);
* Самые популярные позиции (топ-5 позиций по количеству поданных резюме);
* Облако тегов с технологическими тегами (со ссылками на резюме для рекрутеров или на позиции для кандидатов);
* Статистику (например, количество резюме, созданных за последние 24 часа, общее число позиций, общее число кандидатов, общее число рекрутеров, общее число поданных резюме).

# Дополнительно
Приложение должно поддерживать два языка интерфейса: английский и один дополнительный (например, польский, испанский, узбекский, грузинский и т. д.). Пользователь выбирает язык, и его выбор сохраняется. _Переводится только интерфейс_ — пользовательский контент, такой как описания проектов или названия, не переводится.

Приложение также должно поддерживать две визуальные темы: светлую и тёмную. Пользователь выбирает тему, и его выбор сохраняется.

***Требования***:
* Используйте CSS-фреймворк (например, Bootstrap — или любой другой фреймворк и набор UI-компонентов на ваш вкус);
* Поддерживайте адаптивный дизайн для различных размеров экранов и разрешений, включая мобильные телефоны;
* Используйте ORM (например, Sequelize, Prisma, TypeORM, Entity Framework — подойдёт любая);
* Используйте движок полнотекстового поиска — либо через внешнюю библиотеку, либо через встроенные возможности базы данных.

***НЕЛЬЗЯ***:
* Не выполняйте полное сканирование базы данных сырыми запросами SELECT *;

Да, понимание правильное почти целиком. Разберу по пунктам и уточню две неточности в формулировках.

  Что ты описал верно

  Атрибуты — единый справочник. Таблица attribute — это определения (название, категория, тип, описание). Одна на всю систему, общая для профилей, позиций и резюме. Рекрутеры ей управляют совместно.

  У позиции — список привязанных атрибутов и условия. Две отдельные таблицы:
  - position_attribute (position_id, attribute_id, порядок) — какие поля попадут в резюме по этой позиции;
  - access_rule (position_id, attribute_id, оператор, операнд) — кому разрешено создавать это резюме.

  Это разные вещи, хотя обе ссылаются на атрибуты. Позиция может требовать IELTS > 7.0 в правиле доступа, но не выводить IELTS в самом резюме — и наоборот.

  У пользователя есть привязка к атрибутам. Да — attribute_value (profile_id, attribute_id, значение). Это и есть EAV-таблица со значениями.

Две поправки к формулировкам

  1. EAV — это таблица значений, а не справочник

  Ты назвал EAV-таблицей attribute. Точнее наоборот:

  ┌─────────────────┬──────────────────────────────────────┬────────────────────────────────┐
  │     Таблица     │               Что это                │           Роль в EAV           │
  ├─────────────────┼──────────────────────────────────────┼────────────────────────────────┤
  │ attribute       │ название, тип, категория             │ Entity-Attribute — определения │
  ├─────────────────┼──────────────────────────────────────┼────────────────────────────────┤
  │ attribute_value │ profile_id + attribute_id + значение │ Value — сами данные            │
  └─────────────────┴──────────────────────────────────────┴────────────────────────────────┘

  EAV — это именно attribute_value: строка вместо колонки. attribute — обычный справочник. На защите терминология может всплыть.

  2. Резюме НЕ содержит данные пользователя

  Вот это ключевое место, и оно у тебя сформулировано неточно: «резюме содержит связку позиция + атрибуты + пользователь и его данные из профиля».

  Резюме содержит только связку:

  cv: id, candidate_id, position_id, status, version

  Никаких значений внутри. Данные лежат в профиле и подтягиваются при рендере через JOIN. Причина — требование ТЗ: «редактирование атрибута в резюме изменяет исходное значение в профиле». Значение существует ровно в одном месте.

  Практическое следствие: заполнил GPA в резюме на Business Analyst — оно автоматически появилось и в резюме на Data Analyst, потому что это буквально одна и та же строка в attribute_value.

  Как создаётся резюме — по шагам

  Да, позицию выбрать обязательно. Без неё резюме не существует: именно позиция задаёт, какие поля показывать.

  Шаг 1. Кандидат видит список доступных позиций. Не все подряд — только те, где is_public = true или его значения атрибутов удовлетворяют всем access_rule. Проверка одним запросом с EXISTS-подзапросами, не циклом.

  Шаг 2. Создание. POST /api/positions/{id}/cv. Сервер проверяет доступ повторно (клиенту верить нельзя) и уникальность пары кандидат+позиция — не более одного резюме на позицию. Создаётся одна строка со статусом draft.

  Шаг 3. Открытие страницы. Сервер берёт список атрибутов из position_attribute и делает LEFT JOIN на attribute_value профиля этого кандидата:
  - значение есть → показывается заполненным;
  - значения нет → NULL → пустое поле, подсвеченное красным.

  Именно LEFT JOIN (а не INNER) даёт незаполненные поля вместо их исчезновения.

  Шаг 4. Заполнение. Кандидат правит поле inline. Запись идёт в attribute_value его профиля — INSERT, если строки не было, UPDATE, если была. В таблицу cv при этом ничего не пишется.

  Шаг 5. Публикация. Кнопка «Опубликовать» активна, только когда заполнены все атрибуты позиции. Проверка обязательно на сервере. Статус draft → published, после чего резюме видят рекрутеры.
